## 1. 文档用途

本文回答“接下来做什么、按什么顺序做、做到什么程度才算完成”。

- `开发计划.md`：记录未来路线、阶段顺序、验收门槛和待决策事项；
- `进度.md`：记录已经发生的事实、测试证据、阻塞项和 Git 状态；
- `design.md`：记录已经确认的页面、流程、状态、交互和视觉要求；
- `PRD.md`：定义产品范围和业务规则，其他文档与其冲突时以 PRD 为准。

四份核心文档只保留各自所需颗粒度：PRD 管产品边界，设计说明管页面与交互，本计划管实施顺序和门槛，进度只记录已发生且有证据的事实。历史技术说明材料不再作为当前开发的前置批准文件。

计划变更不等于功能完成。每个阶段完成后，必须把实际结果同步到 `进度.md`。

## 2. 当前基线

截至 2026-10-07，V1.1 设计与可点击原型已经确认，项目处于“同步四份核心文档，随后进入正式前端实现”的位置。V1.0 已废弃。

### 2.1 已具备

- 主分支已包含 AionUi、AionCore 和项目文档；
- 桌面技术路线已确定：AionUi（Electron + React）＋ AionCore（Rust + Axum）＋ SQLite ＋本地文件存储；
- Windows 环境的前端构建、AionCore 启动和桌面应用启动已有通过记录；V1.1 完整业务链路的真实模型端到端验收尚未完成；
- 分层测试门禁已经建立，日常改动不再要求每次都执行全仓库回归；
- V1.1 前端需求、设计说明和可点击 HTML 原型已经确认；
- 原型明确了工作台、新对话、最近项目、最近对话、未关联项目、助手选择等核心入口。

### 2.2 尚未完成

- 原型界面尚未正式写入 AionUi 生产代码；
- 项目列表、项目工作区和项目持久化尚未形成完整产品闭环；
- “输入资料 → AI 分析 → 用户确认 → 生成并保存 PRD”尚未完成端到端实现；
- 文档解析、质量评测、失败恢复、打包安装等后续能力尚未完成；
- 本轮已经开始同步 `进度.md`、PRD 和设计说明的 V1.1 口径；修改尚未提交或推送。

## 3. 总体路线

桌面端 V1.1 只覆盖 PRD 阶段 0 至阶段 3。阶段 4 的云端、多用户和商业化能力不进入本轮开发，必须另写 PRD、技术方案和成本安全评估后再决定。

```text
阶段 0：基线与设计确认（基本完成）
  ↓
阶段 1：正式前端与核心纵切闭环
  ↓
阶段 2：资料处理与输出质量
  ↓
阶段 3：桌面 MVP 完整性与交付
  ↓
阶段 4：云端与多人协作（暂不启动）
```

PRD 使用产品交付阶段描述范围，本计划使用 M0～M8 拆解实际开发，二者对应关系如下：

| PRD 产品阶段 | 开发里程碑 | 颗粒度关系 |
|---|---|---|
| 阶段 0：基线与设计确认 | M0 | 文档、代码基线和开工边界收口 |
| 阶段 1：最小纵向切片 | M1～M3 | 先落地前端外壳，再完成持久化与完整纵切闭环 |
| 阶段 2：资料与质量闭环 | M4～M5 | 资料导入、来源控制、输出质量和局部重生成 |
| 阶段 3：桌面 MVP 完整化 | M6～M7 | 恢复、安全、导出、备份、打包和桌面验收 |
| 阶段 4：云端版 | M8 | 暂缓，另立项 |

## 4. 阶段计划

### M0：计划确认与开发基线收口

**目标**

在修改生产代码前，确认路线、首个交付物和验收方法，消除文档与实际状态的差异。

**工作内容**

- 用户审查本开发计划；
- 复核 `PRD.md`、`design.md` 与 HTML 原型的边界；
- 更新 `进度.md` 的最新基线和真实验证证据；
- 确认正式开发从最新 `main` 创建独立功能分支；
- 记录生产代码改造范围，避免直接照搬原型的演示数据和假交互。

**完成门槛**

- 用户确认阶段顺序、首个前端交付物和测试节奏；
- 四份核心文档职责一致且没有明显冲突；
- Git 分支、基线提交和工作区状态有明确记录。

### M1：正式前端外壳与高频入口

**目标**

把已确认的 V1.1 原型中的“正式前端外壳与高频入口”落到 AionUi，让用户能清楚进入工作台、新对话和最近内容。项目持久化和完整业务流程不在 M1 一次性实现，按 M2～M6 分阶段完成。

**工作内容**

- 实现左侧导航、工作台首页、新对话入口和基础窗口布局；
- 实现最近项目、最近对话和未关联项目的展示规则；
- 实现“需求与 PRD 助手”的默认选择及其他助手入口；
- 接入已有路由、状态管理和本地化体系，不创建第二套前端架构；
- 补齐空状态、加载状态、错误状态和不可用状态；
- 保持视觉方向：创新度 4/10、动效 2/10、信息密度 8/10。

**本阶段不做**

- 不在首页伪造完整 AI 业务闭环；
- 不提前做云端账户、团队权限和在线协作；
- 不因原型方便而绕开 AionUi 现有组件和数据流。

**完成门槛**

- 入口、导航和主要状态与 `design.md` 一致；
- 用户可从工作台进入新对话，并能区分项目内会话与未关联会话；
- 关键交互具备可操作演示和针对性自动测试；
- 用户完成一次前端视觉与交互验收。

### M2：项目骨架与本地持久化

**目标**

建立后续核心流程依赖的项目容器，使资料、会话、分析和 PRD 都有明确归属。

**工作内容**

- 项目创建、重命名、打开和最近访问；
- 项目工作区基础页签与空状态；
- 项目、会话、资料、分析结果和 PRD 的最小数据关系；
- SQLite 与本地文件的职责划分、路径规则和异常处理；
- 旧数据兼容或迁移策略；
- 前后端接口契约和错误码约定。

**完成门槛**

- 创建项目后，重启应用仍能恢复项目和必要状态；
- 未关联会话可以保持独立，后续具备归入项目的明确路径；
- 不同项目的数据不会串用；
- 核心数据模型、接口和恢复规则有测试覆盖。

### M3：核心纵切闭环

**目标**

完成 V1 最重要的一条可交付业务链路。

```text
创建或进入项目
→ 输入产品想法、业务需求或粘贴文本资料
→ AI 生成结构化需求分析
→ 用户编辑并确认
→ AI 生成结构化 PRD
→ 用户编辑、保存并再次打开
```

**工作内容**

- 输入方式、资料选择和本次上下文提示；
- AI 分析过程、流式输出、停止、重试和失败恢复；
- 待确认问题、人工编辑和确认动作；
- PRD 生成、编辑、保存、版本状态和重新打开；
- 模拟模型自动化测试；
- 至少一次真实模型端到端冒烟测试。

**完成门槛**

- 正常流程可以从项目入口走到已保存 PRD；
- 用户确认前不会生成“正式 PRD”；
- 中断、失败和重试不会静默丢失已经保存的内容；
- 模拟模型测试通过，并留存真实模型冒烟记录；
- 用户按真实产品任务完成一次端到端验收。

### M4：资料导入与来源控制

**目标**

让产品经理能够使用常见资料工作，并清楚知道 AI 本次引用了什么。

**工作内容**

- 纯文本和 Markdown 导入；
- 可复制文本的 PDF 解析；
- 常规 `.docx` 解析；
- 资料列表、解析状态、失败原因和重新解析；
- 本次生成所用资料的选择与展示；
- 文件大小、格式和隐私提示。

**完成门槛**

- 支持范围内的样本能稳定解析，失败文件有明确原因；
- 用户能控制本次生成使用哪些资料；
- AI 输出可追溯到所选资料，不默认混入其他项目内容；
- 不支持的扫描 PDF、复杂排版等场景有清楚边界。

### M5：输出质量与可控修改

**目标**

把“能生成”提升为“产品经理可以使用、检查和继续修改”。

**工作内容**

- 需求分析和 PRD 的结构完整性检查；
- 信息不足时的追问规则；
- 按章节重新生成，不覆盖用户未授权修改的内容；
- 用户故事、验收标准、范围和风险的质量规则；
- 建立不少于 10 组的代表性验收样本；
- 记录模型、输入资料、关键设置和输出结果。

**完成门槛**

- 代表性样本中至少 8/10 达到约定质量标准；
- 重新生成单个章节不会破坏其他已确认章节；
- 信息不足、模型失败和内容冲突都有可恢复处理；
- 用户确认输出已经达到日常试用水平。

### M6：桌面 MVP 完整性

**目标**

补齐长期使用必须具备、但不直接体现在主流程中的能力。

**工作内容**

- 任务恢复、草稿恢复和异常退出恢复；
- 模型、执行器、存储位置等设置页；
- Markdown 导出；
- 数据备份、恢复和删除确认；
- 密钥安全存储和日志脱敏；
- 无网络、后端不可用、磁盘不可写等错误处理；
- 基本性能、可访问性和隐私检查。

**完成门槛**

- 异常退出后可恢复已保存工作，未保存内容有明确提示；
- 密钥和敏感内容不出现在普通日志中；
- 备份与恢复完成至少一次真实演练；
- 核心错误场景有明确提示和下一步操作。

### M7：Windows 打包与阶段验收

**目标**

交付可安装、可启动、可卸载、可复测的桌面 MVP。

**工作内容**

- Windows 安装包与版本信息；
- 全量测试门禁和构建验证；
- 干净环境安装、首次启动、升级和卸载验证；
- 最终验收清单、已知问题和回滚说明；
- README、进度、操作说明和发布记录同步。

**完成门槛**

- 安装包在约定 Windows 环境可安装并正常启动；
- 核心纵切流程在安装版中通过；
- 全量门禁通过，或遗留问题经过用户明确接受；
- 文档、版本号、安装包和 Git 发布状态一致。

### M8：云端与多人能力（暂缓）

以下内容不属于桌面 V1.1：账号体系、云同步、多人协作、团队权限、在线计费和云端部署。只有在 M7 完成且用户单独批准后，才启动新的产品和技术设计。

## 6. 测试门禁

不要求每次小改动都跑全仓库测试，但不能省略与改动风险相匹配的验证。

| 场景 | 最低验证要求 |
|---|---|
| 文档改动 | 链接、格式、引用和 Git 差异检查 |
| 单个前端组件或交互 | 相关单元/组件测试＋类型检查＋手工交互检查 |
| 前端页面或流程 | 相关测试＋构建检查＋关键路径手工验证 |
| 后端接口或数据模型 | Rust 相关测试＋接口验证＋数据恢复检查 |
| 跨前后端里程碑 | 集成测试＋桌面启动验证＋用户验收 |
| PR 合并、阶段验收或发布 | 全量测试门禁＋生产构建＋安装或运行验证 |

若发现与本次改动无关的上游失败，应单独记录和隔离，不能把它伪报成本次功能通过，也不应未经判断顺手大改上游代码。

## 7. 分工与确认点

### AI 负责

- 前端、后端、数据库和文件处理的实现；
- 自动测试、手工验证、问题修复和构建打包；
- 技术文档、进度证据和 Git 状态整理；
- 在执行提交、推送、合并和发布前说明当前状态与影响。

### 用户负责

- 产品范围、页面和交互取舍；
- 模型账号、API Key 和需要用户持有的外部服务权限；
- 各阶段产品验收；
- 是否提交、推送、合并和发布的最终决定。

## 8. 进度同步规则

### 每次恢复工作时

1. 阅读 `PRD.md`、`design.md`、本计划和 `进度.md`；
2. 检查当前仓库、分支、工作区和远程状态；
3. 明确本轮只推进一个可验收目标；
4. 说明本轮会改什么、不会改什么。

### 每个里程碑结束时

在 `进度.md` 中记录：

- 实际完成内容；
- 未完成内容和原因；
- 测试命令、结果和人工验收证据；
- 当前提交、分支、PR 和远程状态；
- 下一步以及需要用户确认的事项。

只有当范围、顺序、门槛或重要依赖发生变化时，才修改本计划。普通开发进展只更新 `进度.md`。

## 9. 主要风险

| 风险 | 可能后果 | 当前应对 |
|---|---|---|
| 上游代码体量大、结构复杂 | 小改动影响既有能力 | 复用现有架构，按功能分支小步集成 |
| 原型与生产组件存在差异 | 正式实现无法完全照搬 | 以业务行为和验收标准为准，允许等价实现 |
| 数据模型过早固化 | 后续资料和版本能力难扩展 | M2 先定义最小关系和迁移边界 |
| 模型输出不稳定 | 同一流程质量波动 | 模拟测试＋真实冒烟＋代表性样本集 |
| 文档格式复杂 | PDF/DOCX 解析失败或丢信息 | 明确支持边界，失败可见，不承诺 OCR |
| 密钥和资料泄露 | 本地隐私与安全风险 | 安全存储、日志脱敏、项目隔离 |
| 过早做云端 | 延误桌面核心价值 | M8 暂缓，桌面 V1.1 验收后另立项 |

## 10. 计划获批后的前三步

1. 更新 `进度.md`，把已经验证的运行、真实模型和设计状态写准；
2. 从最新 `main` 创建 M1 功能分支，开始修改 AionUi 正式前端；
3. 先交付“导航＋工作台首页＋新对话＋最近项目/对话”的可运行版本，完成针对性测试后交给用户验收。
