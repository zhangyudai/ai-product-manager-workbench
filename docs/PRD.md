# 产品经理 AI 工作台 V1.0 PRD

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 产品名称 | 产品经理 AI 工作台 |
| 版本 | V1.0 MVP |
| 文档状态 | 已按技术栈、前端与部署手册补齐产品级约束，待技术适配确认与第一阶段开发 |
| 目标形态 | 单用户、本地优先的桌面工作台 |
| 核心能力 | 需求与 PRD 助手 + 项目资料管理 |
| 现有基础 | 优先基于 AionUi（桌面端）与 AionCore（本地后端）做增量二开 |
| 确定技术路线 | AionUi（Electron + React）＋ AionCore（Rust + Axum）＋ SQLite ＋ 本地文件存储 |

## 2. 产品定位

面向独立产品经理和中小团队产品负责人的 AI 项目工作台，以项目为单位统一管理访谈记录、会议纪要、竞品资料和历史需求，并基于这些资料完成需求分析、PRD、用户故事及验收标准的生成与维护。

产品口号：

> 把散落的项目资料，变成可执行、可追溯的产品需求。

### 2.1 产品价值

- 将产品想法和零散资料集中到同一个项目中；
- 通过 AI 提炼需求，而不是只生成一篇孤立文档；
- 在生成 PRD 前安排用户确认，减少 AI 自行假设；
- 保存项目资料、分析结果、PRD 和对话，方便持续迭代；
- 为熟悉 AI 工具的用户保留模型和执行器选择能力。

### 2.2 与普通 AI 文档工具的区别

V1.0 不把“输入一句话生成 PRD”作为唯一价值，而是提供一条连续工作流：

```text
项目资料沉淀
→ AI 需求分析
→ 用户确认
→ 结构化 PRD
→ 后续继续修改和复用
```

## 3. 目标用户

### 3.1 核心用户

需要独立完成需求整理和 PRD 编写、经常使用 AI、同时管理多个项目的个人产品经理。

### 3.2 用户特征

- 手中经常有想法、会议纪要、访谈记录或业务需求；
- 资料散落在文档、聊天记录和本地文件中；
- 希望 AI 帮助梳理，但仍要自己确认关键结论；
- 可能使用不同模型，并希望在必要时切换；
- 不希望第一版包含复杂的团队权限和审批流程。

### 3.3 V1.0 使用模式

- 单用户；
- 本地优先；
- 不做组织、成员、角色和复杂权限；
- 不以企业采购和多人协作为首版目标。

## 4. 核心使用场景

V1.0 同时允许三种入口创建项目：

1. **从产品想法开始**：用户输入一段想法，由 AI 帮助补全需求；
2. **从现有资料开始**：用户导入访谈、会议或竞品资料，由 AI 提炼需求；
3. **从业务需求开始**：用户粘贴业务方提出的需求，由 AI 进行分析和结构化。

第一版重点优化：

> 从产品想法或现有资料出发，经过 AI 分析和用户确认，生成结构化 PRD。

## 5. V1.0 核心业务闭环

```text
用户进入工作台
→ 创建产品项目
→ 选择开始方式：产品想法 / 导入资料 / 业务需求
→ 系统默认选择“需求与 PRD 助手”
→ 系统使用项目默认模型和执行方式
→ 用户输入内容或导入资料
→ AI 分析资料并输出结构化需求和待确认问题
→ 用户修改并确认关键需求
→ AI 根据已确认内容生成结构化 PRD
→ 用户编辑并保存 PRD
→ 按需生成用户故事和验收标准
→ 系统保存项目资料、分析结果、对话和 PRD
→ 用户下次打开项目继续工作
```

### 5.1 闭环中的人工确认点

- AI 完成需求分析后，用户需要检查和修改；
- 用户确认关键需求后，才能生成正式 PRD；
- AI 生成的用户故事和验收标准可以继续编辑；
- 系统不得把 AI 推测自动标记为用户已确认事实。

## 7. 页面与功能需求

### 7.1 工作台首页

#### 目标

让用户快速开始新工作或继续最近的项目。

#### V1.0 功能

- 创建项目；
- 查看并打开最近项目；
- 查看最近对话；
- 查看正在运行的任务；
- 快捷入口：从产品想法开始；
- 快捷入口：导入现有资料。

### 7.2 项目列表

#### V1.0 功能

- 创建项目；
- 按项目名称搜索；
- 打开项目；
- 置顶项目；
- 删除项目，删除前二次确认；
- 显示项目名称和最后更新时间。

#### 暂不实现

- 项目归档；
- 多层分类；
- 批量操作；
- 团队项目与权限。

### 7.3 项目工作区

#### 顶部信息

- 项目名称；
- 当前助手；
- 当前模型；
- “更多设置”入口。

项目顶部不显示“当前阶段”，避免增加不必要的流程管理负担。

#### 内部页面

- 项目概览；
- 项目资料；
- 需求分析；
- PRD。

### 7.4 项目资料

#### 目标

保存本项目中 AI 分析时可以使用的原始资料。

#### V1.0 功能

- 上传文件；
- 粘贴文本；
- 添加本地文件夹；
- 查看资料列表；
- 预览资料内容；
- 显示解析成功或失败；
- 删除资料。

#### V1.0 文件边界

- 必须支持纯文本、Markdown、可复制文字的 PDF 和 Word（`.docx`）；
- Word 解析至少应提取正文、标题、段落、列表和表格中的文字，并尽量保持原有阅读顺序；
- V1.0 不承诺老式 `.doc`、加密 Word、宏、批注、修订记录、复杂排版和嵌入对象的完整解析；
- 单个文件默认上限 20 MB，超限时在上传前明确提示；
- 不承诺扫描件 OCR、图片内容识别、音视频转写和加密文档解析；
- 解析失败时保留原文件、失败原因和重试入口，不把空解析结果当作成功。

#### 暂不实现

- 复杂标签体系；
- 高级全文搜索；
- 资料关系图；
- 复杂版本管理；
- 批量资料处理；
- 自定义解析参数。

### 7.5 需求分析

#### 目标

将用户输入和项目资料整理成可确认的需求结论，为生成 PRD 做准备。

#### 输出内容

- 产品目标；
- 目标用户；
- 用户场景；
- 用户痛点；
- 核心需求；
- MVP 范围；
- 待确认问题。

#### 用户操作

- 触发 AI 分析；
- 编辑分析结果；
- 删除不正确的内容；
- 确认分析结果；
- 查看本次分析使用了多少份项目资料。

#### 暂不实现

- 逐条接受或拒绝；
- 事实与推测的复杂标签；
- 需求冲突管理；
- 优先级计算模型；
- 来源关系图；
- 分析版本对比。

### 7.6 PRD 工作区

#### 目标

根据用户已确认的需求生成并维护结构化 PRD。

#### 默认 PRD 结构

1. 产品背景；
2. 产品目标；
3. 目标用户；
4. 核心场景；
5. 功能范围；
6. 核心业务流程；
7. 功能需求；
8. 非功能要求；
9. 用户故事与验收标准；
10. 暂不实现范围；
11. 待确认问题。

#### V1.0 功能

- 根据已确认需求生成 PRD；
- 在线编辑 PRD；
- 自动保存，并支持手动保存；
- 单独重新生成某一章节；
- 导出 Markdown 文件；
- 将用户故事和验收标准作为 PRD 中的可选章节生成。

#### 暂不实现

- 独立的用户故事页面；
- 三栏复杂编辑器；
- 文档版本对比；
- 来源关系侧栏；
- 评论与审批；
- Word、PDF 等多格式导出。

### 7.7 新会话

#### 目标

允许用户进行临时问答，或围绕指定项目继续处理资料和需求。

#### V1.0 功能

- 新建对话；
- 选择关联项目；
- 选择助手；
- 选择模型；
- 输入文字；
- 上传文件；
- 查看 AI 回答；
- 停止生成；
- 重新生成。

关联项目后，对话默认可以使用该项目的资料。

#### 暂不实现

- 对话分支；
- 多结果并排比较；
- 对话标签；
- 高级模型参数；
- 多 Agent 协作编排。

### 7.8 任务中心

#### V1.0 功能

- 查看正在执行的 AI 任务；
- 查看已完成和失败的任务；
- 显示任务所属项目；
- 停止正在执行的任务；
- 对失败任务进行重试。

任务中心仅承担运行状态查看，不做复杂的项目进度管理。

### 7.9 设置

#### V1.0 功能

- 配置模型服务；
- 测试模型连接；
- 设置默认模型；
- 查看 Codex/Pi 是否可用；
- 设置默认执行方式；
- 设置本地数据保存位置；
- 设置主题和语言；
- 查看应用版本。

## 8. 助手、执行器与模型规则

### 8.1 三个概念

| 层级 | 用户看到的例子 | 作用 |
|---|---|---|
| 助手 | 需求与 PRD 助手、产品经理开发助手、通用助手 | 决定当前要完成什么工作 |
| 执行器 | 自动、Codex CLI、Pi | 决定任务由哪套 Agent 能力执行 |
| 模型 | GPT、Claude、Gemini、DeepSeek 等 | 决定使用哪个大模型 |

### 8.2 V1.0 交互原则

- “助手”是用户的主要选择，直接显示；
- “模型”可以显示，但默认使用项目默认模型；
- “执行器”放在“更多设置”中，默认选择“自动”；
- 普通 PRD 生成不要求用户理解 Codex 或 Pi；
- 用户主动切换后，系统记住该项目的选择；
- 执行器不可用时，应提示原因，并允许改回“自动”或其他可用方式；
- Codex 更适合代码仓库和开发类任务，不作为普通 PRD 生成的强制依赖。
- V1.0 不在 PRD 中绑定具体模型厂商和模型名称；
- 用户通过 OpenAI 兼容接口或已支持的模型服务，自行填写接口地址、API Key 和模型标识；
- 核心闭环只依赖文本对话、流式输出和结构化文本生成，不强制依赖视觉、联网、工具调用等特定模型能力；
- 真实冒烟时，由测试人员临时配置至少一个真实可用的模型接口，并在测试记录中登记当次使用的厂商和模型；
- 开发期允许使用 mock 验证流程，但不得用 mock 结果代替真实模型验收；
- 调用模型前应让用户知道将使用哪些项目资料；
- V1.0 采用用户自带 API Key，模型费用由用户自己的模型厂商账户结算，产品方不统一承担模型账单；
- 系统通过单任务输入/输出 Token 上限、最多重试次数和“同时只运行一个主要生成任务”控制异常消耗；
- 系统记录调用次数与 Token 用量；若用户填写模型单价，可显示估算费用并设置月度提醒，但不把币种费用硬限制作为 V1.0 上线条件。

### 8.3 默认规则

```text
创建项目
→ 默认助手：需求与 PRD 助手
→ 默认执行器：自动
→ 默认模型：用户在设置中配置的模型标识
→ 未配置模型：引导用户填写接口地址、API Key 和模型标识
```

## 9. 核心数据对象

V1.0 只保留完成闭环所需的数据：

| 对象 | 主要内容 |
|---|---|
| 项目 | 名称、创建时间、更新时间、默认助手、默认模型、默认执行器 |
| 项目资料 | 文件或文本、解析状态、所属项目 |
| 需求分析 | 分析内容、确认状态、确认人、确认时间、更新时间 |
| PRD | 标题、正文、保存时间、所属项目 |
| 对话 | 消息内容、关联项目、使用的助手和模型 |
| 任务 | 类型、运行状态、进度、失败原因、恢复信息、所属项目 |

所有重要对象必须持久化。应用异常退出或电脑重启后，已保存内容、人工确认状态和未完成任务的可恢复信息不得只存在于内存中。

## 10. Agent 效果验收标准

### 10.1 验收样本

在进入 V1.0 验收前，准备不少于 10 个代表性样本，至少覆盖：一句产品想法、较完整业务需求、会议纪要、用户访谈、竞品资料、信息缺失资料、相互矛盾资料、无关内容混入、长文档和解析失败文件。

### 10.2 需求分析质量

- 至少 8/10 个样本能够产出完整的产品目标、目标用户、核心场景、核心需求、MVP 范围和待确认问题；
- 对缺失或冲突信息必须提出待确认问题，不得把推测写成用户已确认事实；
- 10/10 个样本都不得伪造资料中不存在的来源、数字或用户结论；
- 用户修改后再次生成时，已确认内容不得被无提示覆盖。

### 10.3 PRD 质量

- 至少 8/10 个样本生成的 PRD 章节完整、逻辑一致，并能追溯到已确认的需求分析；
- 至少 8/10 个样本经产品经理不超过两轮修改后达到“可进入原型评审”的标准；
- 单章节重新生成不得覆盖其他章节或用户手工修改；
- 个别措辞、标点和排版瑕疵可由产品经理人工判断，但结构缺失、范围越界、伪造事实和覆盖确认内容不属于可接受瑕疵。

### 10.4 真实模型验收记录

每次阶段验收至少记录：模型与版本、输入样本、是否使用项目资料、首字等待时间、总耗时、成功或失败、人工评分和主要问题。模型名称、价格和预算上限由验收前的技术适配声明补充，不在 PRD 中预设厂商。

## 11. V1.0 功能验收标准

### 11.1 主流程验收

```text
Given：用户已经配置至少一个可用模型
When：用户创建项目，输入产品想法或导入一份资料，完成需求分析并确认
Then：系统能够生成一份结构化 PRD，用户可以编辑、保存并再次打开
```

### 11.2 项目与资料

- 用户可以创建、搜索、打开、置顶和删除项目；
- 用户可以上传资料或粘贴文本；
- 资料解析成功或失败时有明确状态；
- 用户上传普通 `.docx` 文件后，系统能够提取正文、标题、列表和表格文字，并用于需求分析；
- 解析失败不会删除原文件，用户可以重试；
- 不支持的格式和超限文件在处理前给出可理解提示；
- 关闭并重新打开应用后，项目和资料仍然存在。

### 11.3 需求分析

- AI 能基于用户输入和已选择的项目资料生成结构化分析；
- 分析至少包含产品目标、目标用户、核心需求、MVP 范围和待确认问题；
- 用户可以修改或删除分析内容；
- 未确认分析结果时，系统应提醒用户确认后再生成正式 PRD；
- AI 生成失败时保留用户输入，并允许重试。

### 11.4 PRD

- 系统可以根据已确认需求生成结构化 PRD；
- 用户可以编辑并保存 PRD；
- 用户可以重新生成单个章节，而不覆盖整篇文档；
- 用户可以选择生成用户故事和验收标准章节；
- 用户可以导出 Markdown；
- 重新进入项目后可以继续编辑上次保存的 PRD。

### 11.5 模型与执行器

- 用户可以在项目中查看和切换模型；
- Codex/Pi/自动执行方式可以在“更多设置”中选择；
- 用户不手动选择执行器，也能完成需求分析和 PRD 生成；
- 当前模型或执行器不可用时，系统给出可理解的错误和切换入口；
- 重复点击生成按钮不会创建多个相同任务。
- 至少用一个真实模型跑通主流程；mock 只作为自动化测试手段。

### 11.6 基础状态与恢复

主要页面需要具备：

- 空数据状态；
- 加载状态；
- AI 生成中状态；
- 成功状态；
- 失败与重试状态；
- 停止生成状态；
- 关闭页面后再次进入的数据恢复。
- 应用异常退出后，已保存资料、人工确认结果和 PRD 可恢复；
- 长任务不得因切换页面而无提示消失，失败后应能查看原因并重试。

## 12. V1.0 范围边界

### 12.1 本期必须完成

- 项目创建和管理；
- 项目资料导入和查看；
- AI 需求分析；
- 用户修改与确认；
- 结构化 PRD 生成、编辑、保存；
- 用户故事和验收标准章节生成；
- 项目对话；
- 模型配置与切换；
- Codex/Pi/自动执行方式的基础选择；
- 任务状态与失败重试；
- Markdown 导出；
- 本地数据持久化。

### 12.2 本期明确不做

- 团队、成员和权限管理；
- 审批、评论和通知流程；
- 多 Agent 自动协作；
- 复杂需求优先级模型；
- 资料关系图和知识图谱；
- 独立用户故事管理页面；
- PRD 版本对比；
- Word/PDF 多格式导出；
- 老式 `.doc` 和复杂 Word 内容的完整解析；
- 企业系统深度集成；
- 完整研发项目管理；
- 移动端。

## 13. 交付阶段

| 阶段 | 交付重点 | 进入下一阶段的条件 |
|---|---|---|
| 阶段 0：基线确认 | 获取并固定 AionUi/AionCore 基线版本，完成许可证、启动方式、现有能力和未提交修改检查 | 两个项目可在 Windows 本地启动，现有能力与改动边界有记录 |
| 阶段 1：最小纵向切片 | 创建项目 → 输入想法/导入文本 → AI 需求分析 → 人工确认 → 生成并保存 PRD | 主流程可操作，mock 自动化测试通过，真实模型完成至少 1 条冒烟 |
| 阶段 2：资料与质量闭环 | 完成纯文本、Markdown、可复制文字 PDF 和普通 `.docx` 的稳定解析，以及资料选择、待确认问题、单章节重生成和效果测试集 | 第 10 节质量指标与第 11 节相关验收通过 |
| 阶段 3：桌面 MVP 完整化 | 任务恢复、设置、错误状态、Markdown 导出、本地数据备份恢复、Windows 打包 | 非功能、安全、恢复和桌面安装验收通过 |
| 阶段 4：云端版设计与验证 | 在桌面 MVP 稳定后，设计公网访问、账号登录、跨设备同步和多人使用能力 | 单独完成云端版 PRD、技术方案、费用评估和安全评审后再启动开发 |

V1.0 默认只推进到阶段 3。阶段 4 已确认需要推进，但属于桌面 MVP 之后的独立版本，不纳入 V1.0 验收，也不得因为部署手册存在就默认创建计费云资源。

## 14. 非功能、安全与数据要求

### 14.1 性能与容量

- 本地项目列表、资料列表和已保存 PRD 的普通操作，目标为 2 秒内出现结果或明确加载状态；
- AI 请求发出后 3 秒内必须出现“已开始处理”的状态，不要求模型在 3 秒内完成；
- 真实模型的首字时间和总耗时在验收中记录，首版不设脱离模型能力的虚假硬指标；
- V1.0 按单用户、同时运行 1 个主要生成任务设计；多任务并发不是首版目标。

### 14.2 密钥与隐私

- 模型 Key 不得写入代码、仓库、前端日志或导出文件；界面回显必须脱敏；
- 项目资料默认保存在本机。只有用户触发模型任务时，才把完成该任务所需的最小内容发送给所选模型服务；
- 日志不得记录密钥、完整项目资料和完整模型输入输出；错误信息不得向用户暴露内部堆栈；
- 上传文件必须校验扩展名、真实内容类型、大小和安全文件名，阻止路径穿越；
- 删除项目、资料或 PRD 前必须二次确认，并明确影响范围。

### 14.3 数据恢复与备份

- 数据结构变更必须带迁移与回滚方案，不得静默丢弃旧数据；
- 用户可将项目核心数据和 PRD 导出到自己选择的位置；
- 阶段 3 必须验证一次“备份后恢复”与一次“异常退出后重新打开”；
- 桌面 MVP 后需要建设云端版，支持公网访问、跨设备同步和多人使用；正式部署前必须先确定登录隔离、租户与权限、业务数据持久化、文件对象存储、同步冲突和可恢复方案，不得把临时目录当作可靠存储。

### 14.4 可用性与可访问性

- 核心操作可通过键盘完成，按钮和输入控件具有可理解名称；
- 加载、空数据、等待确认、生成中、停止、失败、断线与恢复状态必须可区分；
- V1.0 以 Windows 桌面端为验收终端，不将手机响应式作为桌面版完成条件。

## 15. 已确认决策与待确认项

### 15.1 已确认决策

1. V1.0 不在 PRD 中指定模型厂商和模型名，采用用户自带 API Key 与可配置模型标识；
2. 真实冒烟测试时临时登记实际使用的厂商和模型，不把测试配置固化为产品依赖；
3. 模型费用由用户自己的厂商账户结算，通过 Token、重试和并发限制控制异常消耗；
4. V1.0 阶段 2 必须稳定解析普通 Word（`.docx`）文件，老式 `.doc` 和复杂嵌入内容除外；
5. 桌面 MVP 完成后需要建设云端版，目标包括公网访问、跨设备同步和多人使用；
6. 云端版单独编写 PRD 和技术方案，不纳入桌面 V1.0 的验收范围。

### 15.2 后续待确认

1. 本地数据默认保留多久，以及用户期望的备份位置；
2. 云端版的首批用户角色、基本权限和收费方式。

## 16. MVP 成功判断

V1.0 达标的核心不是页面数量，而是用户能够独立完成以下过程：

> 创建一个项目，放入想法或资料，通过 AI 得到可修改的需求分析，确认后生成并保存一份可继续维护的 PRD。

只要这条主链路稳定、清楚、可恢复，V1.0 就具备进入原型和开发验证的条件。
