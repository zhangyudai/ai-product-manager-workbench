# 产品经理 AI 工作台｜技术适配声明

> 状态：基于当前 PRD、三份手册和上游公开资料形成的开工前声明。当前工作区只有文档，没有 AionUi/AionCore 源码，因此代码基线、可运行状态和已有本地改动仍待获取后复核。

> 确定技术路线：AionUi（Electron + React）＋ AionCore（Rust + Axum）＋ SQLite ＋ 本地文件存储。V1.0 不迁移到 Python/FastAPI、Next.js 或 veFaaS。

## 1. 产品形态判断

- 产品类型与核心任务：单用户、本地优先的产品经理桌面工作台；把产品想法和项目资料转为可确认的需求分析与可继续编辑的 PRD。
- 核心交互：多轮对话 + 分阶段确认 + 长文档编辑 + 动态模型/执行器调用。
- 开发路径：采用最小纵向切片。第一阶段直接打通“创建项目 → 输入/导入 → 需求分析 → 人工确认 → 生成并保存 PRD”，不先重做整套视觉。
- 主要终端：V1.0 为 Windows 桌面端。
- 当前阶段范围：先完成代码基线和本地运行自检，再实现 PRD 阶段 1；不包含云部署。

## 2. 采用的现有方案

- AionUi：继续作为 Electron 桌面端和现有 React 交互基础，避免另建平行的 Next.js 前端。
- AionCore：继续作为 Rust 本地后端，复用现有 HTTP/WebSocket、SQLite、会话、项目、文件、认证和 Agent 能力。
- SQLite 与本地文件：符合单用户、本地优先定位；业务数据、文件元数据和长任务状态必须可恢复。
- 现有 API 与事件约定：优先增量扩展现有领域，不为了套用手册批量改路径或替换协议。
- 现有测试与构建工具：沿用 AionUi/AionCore 各自工具链，并为新增主流程补单元、契约、集成和端到端测试。

## 3. 触发的按需模块

- 文档解析：由项目资料导入触发；第一阶段先支持文本/Markdown，随后接入可复制 PDF，Word 按 PRD 确认后纳入阶段 2。
- 流式输出：由需求分析和 PRD 长文本生成触发；复用现有实时事件能力。
- 富文本/Markdown 编辑：由 PRD 在线编辑、单章节重生成触发；优先复用现有编辑与预览组件。
- 持久化任务状态：由可停止、失败重试和异常恢复触发；不可只保存在前端状态或进程内存。
- 本地备份与恢复：由本地优先和资料长期保存触发；阶段 3 引入并完成恢复演练。

## 4. 偏离或暂缓的默认方案

- Python + FastAPI：改为现有 Rust + Axum/AionCore；原因是已有后端与产品能力可复用。影响是开发需遵循 Rust 领域模块与 API 约定；只有现有后端无法满足 PRD 且迁移收益明确时才重新评估。
- Next.js + Tailwind：改为现有 AionUi Electron + React 技术栈与组件体系；原因是目标终端是桌面端且已有成熟前端。影响是不直接套用 Web 手册的目录和部署方式，但继续遵守类型、安全、状态和真实界面验收底线。
- 后端先行：改为纵向切片；原因是人工确认、流式反馈和 PRD 编辑属于核心可用性，必须在真实桌面交互中一起验证。
- 火山引擎 veFaaS：当前暂缓；部署手册默认面向 Python/Next.js Web 产品，不能直接当作 Electron/Rust 桌面应用发布方案。阶段 3 先完成 Windows 桌面安装包；只有确认公网访问、跨设备或多人需求后，阶段 4 再为 AionUi WebUI/远程模式单独设计部署方案。
- 多 Agent 自动协作、移动端、复杂权限与云数据库：均按 PRD 暂缓，不提前铺设。

## 5. 强制底线检查

- 密钥与隐私：待代码复核。目标是 Key 不入仓库、不进日志、界面脱敏；只向模型发送完成当前任务所需的最小资料。
- 数据与任务可恢复：待代码复核。项目、资料、确认状态、PRD 和长任务状态必须持久化并经过异常退出恢复测试。
- 输入输出校验：待实现/复核。文件类型、真实内容、大小和安全文件名必须校验；模型结构化输出进入业务层前必须验证。
- 错误与日志边界：待代码复核。用户错误可理解，内部错误可追踪，日志不记录密钥和完整敏感正文。
- 测试与真实模型验收：每阶段先跑 mock 自动化，再用至少一个真实模型做端到端冒烟；按 PRD 第 10、11 节记录和验收，mock 不得冒充真实结果。
- 许可证与归属：保留上游许可证、版权和归属信息；对修改文件留下显著修改说明；发布前对固定版本及第三方依赖再做一次许可证清单审计。

## 6. 需要产品经理决定的问题

1. 第一阶段用于真实冒烟的模型厂商、模型名和费用上限。
2. Word 文件是否必须在 V1.0 阶段 2 完成稳定解析。
3. 桌面 MVP 后是否需要公网访问、跨设备同步或多人使用；这会决定是否启动云端部署设计。

## 7. 开工前仍需完成的自检

1. 将 AionUi 与 AionCore 的目标二开仓库放入同一工作区并固定基线提交；二者应为同级目录。
2. 分别检查 README、AGENTS.md、许可证、依赖锁文件、启动命令、测试、未提交修改和已有数据。
3. 在 Windows 上构建并启动 AionCore，再由 AionUi 启动桌面应用；记录真实版本、端口、数据库位置和失败信息。
4. 盘点现有项目、文件、助手、对话、任务、编辑器和模型配置能力，形成“直接复用 / 局部改造 / 新增”清单。
5. 自检完成后生成《阶段 1 技术开发文档》，再开始编码。

## 8. 二开与发布合规结论

可以基于 AionUi 和 AionCore 二开。当前上游两个仓库的顶层 `LICENSE` 均为 Apache License 2.0，允许使用、修改和分发衍生作品，包括商业使用，但必须遵守许可证条件。发布时至少要做到：

- 随分发物保留 Apache-2.0 许可证副本；
- 保留适用的版权、专利、商标和归属声明；
- 对修改过的上游文件作显著修改说明；
- 若所采用版本含 `NOTICE`，按许可证要求随分发物保留其归属内容；
- 不把 AionUi 名称、Logo 或其他商标许可误解为已获得官方背书，二开产品应使用自己的品牌并注明来源；
- 发布前复核固定提交，因为 AionCore 当前顶层 `LICENSE` 为 Apache-2.0，而工作区 `Cargo.toml` 的包许可证字段标为 MIT，需把这一上游元数据差异和第三方依赖许可证一并记录，不能只看 README 的一句话。

以上是工程合规建议，不替代正式法律意见。
